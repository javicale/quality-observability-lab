# Observability and evidence contract

## Identifiers

- Execution UUID: one `npm run demo` or `npm run demo:stack` invocation; also the evidence directory name.
- `test_run_id`: execution UUID plus scenario. Sent as `x-test-run-id`, stored as `test.run_id` on spans/logs, and returned in scenario JSON.
- Trace ID: 32 lowercase hex characters generated in the test and propagated through W3C `traceparent`.
- Parent span ID: remote test context. It is a propagation anchor, not an exported browser span.
- Server span ID: generated by OpenTelemetry. Logs carry it and the inventory span references it.

The deterministic gate verifies response → server span → child span → log, including exact trace/run IDs and parent relationships. The failing child must contain an exception event; the server must carry error status and HTTP 500. A valid healthy scenario requires HTTP 200 and no span error status.

## Metrics

`lab.http.requests` counts completed checkout operations. `lab.http.duration` measures synthetic operation duration in milliseconds before telemetry flush and network response. It is not browser end-to-end latency. Both use `http.route`, `http.response.status_code`, and `lab.scenario` attributes.

SDK file exports are cumulative snapshots. **Do not sum repeated snapshots**; use the latest point for each attribute set. Run IDs are deliberately excluded from metric labels to avoid high-cardinality series. Metrics therefore join to evidence by controlled execution plus scenario/status rather than by individual trace ID.

## File evidence contract

Each scenario JSON records `schema_version`, `scenario`, `test_run_id`, `trace_id`, `parent_span_id`, expected/actual HTTP status, `outcome`, `injected_failure`, response body and screenshot path. JSONL files contain records emitted through OpenTelemetry SDK exporter interfaces.

`quality-gate.json` explicitly distinguishes healthy checkout PASS, injected checkout FAIL and failure-detection PASS. Missing or malformed files fail closed. Unit tests mutate correlation, parent relationships, child spans, logs, metrics, exceptions and status codes to prove rejection behavior.

## OTLP stack contract

With `OTEL_EXPORTER_OTLP_ENDPOINT` enabled, the same SDK emits traces, logs and metrics through OTLP/HTTP in addition to the local files. `scripts/verify-stack.js` requires all of the following before writing `stack-verification.json` with `stack: PASS`:

- Grafana health succeeds and the `Quality Observability Lab` dashboard is discoverable.
- Tempo can return the exact trace ID for both `success` and `error` scenarios.
- Loki contains `checkout.completed` / `checkout.failed` records whose structured metadata preserves the exact trace ID and `test_run_id`.
- Prometheus exposes the `lab_http_requests` metric family.

The stack contract is intentionally separate from the deterministic evidence gate. Container startup alone is insufficient; CI verifies backend queryability.

## Cross-signal finding

During integration, traces and metrics were successfully ingested while logs were absent. The root cause was an incorrect `SimpleLogRecordProcessor` construction for the current OpenTelemetry JS logs SDK. Fixing the processor configuration restored Loki ingestion. This became a useful test of the lab's premise: partial observability can look healthy unless each signal is independently verified.

## Evidence limitations

Files are not signed or tamper-proof. The local LGTM storage is ephemeral. Metric values are experiment observations, not SLOs. IDs are untrusted correlation input validated for shape, not authentication. No request bodies, credentials, customer payloads or arbitrary headers are logged. The stack verifier proves this controlled topology only; it is not a generic production observability conformance suite.
